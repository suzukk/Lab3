# 1. Гурван сценарио

## 1.1 Performance Scenario

| ---------------------- | -------------------------------------------------------------------------------------------------- |

| **Системийн төлөв**    | API сервер хэвийн ажиллаж, `/cart/add` endpoint хүсэлт хүлээн авах боломжтой байна.                |

# 2. SLO

| Сценарио         | SLI                 | Босго        | Цонх / нөхцөл  |
| ---------------- | ------------------- | ------------ | -------------- |
| **Performance**  | `/cart/add` latency | p95 < 200 ms | 20 VU, 1 минут |
| **Reliability**  | `/pay` error rate   | < 8%         | 20 VU, 1 минут |
| **Availability** | Checks success rate | > 90%        | 20 VU, 2 минут |
| **Report**       | `/report` latency   | p95 < 450 ms | 20 VU, 1 минут |

## 2.1 Availability Error Budget

Availability SLO нь 90% тул:

**Error Budget = 100% − 90% = 10%**

2 минут = 120 секунд.

**120 × 10% = 12 секунд**

Иймээс 2 минутын цонхонд зөвшөөрөгдөх unavailable хугацааны онолын төсөв нь **12 секунд** байна.

> Анхаарах зүйл: k6-ийн `checks` нь хүсэлтийн түвшинд амжилт/алдааг хэмждэг. Тиймээс 10%-ийн error budget-ийг 12 секунд гэж хөрвүүлсэн нь хугацаанд суурилсан онолын эквивалент бөгөөд k6-ийн `checks`-ийн 10%-тай шууд ижил хэмжүүр биш.

# 3. k6 Threshold Test

SLO-уудыг k6 threshold хэлбэрээр дараах байдлаар хэрэгжүүлсэн:

```javascript
thresholds: {
    'http_req_duration{name:cart}': ['p(95)<200'],
    'http_req_failed{name:pay}': ['rate<0.08'],
    'checks': ['rate>0.90'],
    'http_req_duration{name:report}': ['p(95)<450'],
}
```

## 3.1 Pass Test

Хэвийн нөхцөлд 20 VU, 1 минутын тест ажиллуулсан.

| Metric            | Threshold |        Actual | Result |
| ----------------- | --------: | ------------: | ------ |
| Checks            |     > 90% |    **98.05%** | PASS   |
| `/cart/add` p95   |  < 200 ms |   **2.48 ms** | PASS   |
| `/report` p95     |  < 450 ms | **391.91 ms** | PASS   |
| `/pay` error rate |      < 8% |     **5.82%** | PASS   |

Нийт **2781 HTTP request** хийгдсэн бөгөөд **2727 checks амжилттай**, **54 checks амжилтгүй** болсон.

`/pay` endpoint-д зориудаар ойролцоогоор 5%-ийн санамсаргүй 500 алдаа оруулсан тул 5.82%-ийн error rate гарсан боловч 8%-ийн SLO босгоос бага байсан.

# 4. Chaos Test

Chaos test-ийн үед k6 тестийн хугацааг 2 минут болгож, тест үргэлжилж байх үед API серверийг ойролцоогоор 10 секунд зогсоож, дараа нь дахин ажиллуулсан.

## 4.1 Chaos Test Result

| Metric            | Threshold |        Actual | Result |
| ----------------- | --------: | ------------: | ------ |
| Checks            |     > 90% |    **83.95%** | FAIL   |
| `/cart/add` p95   |  < 200 ms |   **2.35 ms** | PASS   |
| `/report` p95     |  < 450 ms | **390.53 ms** | PASS   |
| `/pay` error rate |      < 8% |    **19.43%** | FAIL   |

Нийт **5727 checks**-ээс **4808 нь амжилттай**, **919 нь амжилтгүй** болсон.

Availability:

**4808 / 5727 × 100 = 83.95%**

Ингэснээр 90%-ийн Availability SLO хангагдаагүй.

Мөн нийт checks-ийн **16.04%** нь амжилтгүй болсон нь зөвшөөрөгдөх **10%-ийн error budget**-ээс давсан.

Chaos test-ийн үед `/pay` endpoint-ийн error rate **19.43%** болсон. Үүнд сервер зогссон хугацаанд үүссэн хүсэлтийн алдаанууд нэмэгдсэн.

Энэ тестээс харахад сервер хэвийн ажиллаж байх үед latency-ийн threshold-ууд хангагдаж байсан боловч серверийн availability алдагдахад availability болон reliability-ийн threshold-ууд зөрчигдөж болохыг харуулсан.

# 5. Deliberate Threshold Failure

Threshold-ийг зориудаар хэт хатуу болгож failure үүсгэв.

Анхны threshold:

```text
http_req_duration{name:report}: p(95)<450
```

Дараах байдлаар өөрчилсөн:

```text
http_req_duration{name:report}: p(95)<100
```

`/report` endpoint-ийн бодит p95 latency нь **390.15 ms** байсан.

| Metric            | Threshold |        Actual | Result |
| ----------------- | --------: | ------------: | ------ |
| Checks            |     > 90% |    **98.55%** | PASS   |
| `/cart/add` p95   |  < 200 ms |   **3.04 ms** | PASS   |
| `/report` p95     |  < 100 ms | **390.15 ms** | FAIL   |
| `/pay` error rate |      < 8% |     **4.32%** | PASS   |

k6 threshold failure үүсгэж:

```text
thresholds on metrics 'http_req_duration{name:report}' have been crossed
```

гэж мэдээлсэн бөгөөд k6 exit code:

```text
99
```

гарсан.

Энэ нь threshold нь зөвхөн тайлангийн мэдээлэл биш бөгөөд шаардлага хангаагүй үед тестийг failure гэж тэмдэглэх боломжтойг харуулсан.

# 7. Дүгнэлт

Энэ лабораторийн ажлаар Quality Scenario-оос SLO, SLO-оос k6 Threshold рүү шилжих үйл явцыг хэрэгжүүлсэн. Performance scenario-д `/cart/add` endpoint-ийн p95 latency-г 200 ms-ээс бага байлгах SLO тодорхойлсон. Reliability scenario-д `/pay` endpoint-ийн error rate-ийг 8%-иас бага байлгах зорилго тавьсан. Availability scenario-д серверийн тасалдлын үед checks-ийн амжилтын түвшинг 90%-иас дээш байлгах шаардлага тодорхойлсон. Хэвийн тестийн үед бүх дөрвөн threshold амжилттай хангагдсан. Chaos test-ийн үед серверийг зориудаар зогсоосноор availability 83.95% болж, 90%-ийн SLO зөрчигдсөн. Мөн `/pay` endpoint-ийн error rate 19.43% болж reliability SLO мөн зөрчигдсөн. Deliberate failure тестээр `/report` endpoint-ийн p95 threshold-ийг 100 ms болгож, бодит 390.15 ms үр дүнгээр threshold failure үүсгэсэн. Иймээс threshold нь SLO-г автоматаар шалгаж, туршилтын явцад шаардлага хангагдсан эсэхийг тодорхойлох боломжийг олгосон.
